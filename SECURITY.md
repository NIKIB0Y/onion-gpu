# Security

This program generates long-term identity keys for Tor onion services. A weakness
in it translates directly into someone else being able to impersonate a service.

## Reporting

Open a GitHub issue for anything that is not itself exploitable. For a finding that
would let an attacker recover generated keys, please use GitHub's private
vulnerability reporting (Security → Report a vulnerability) instead of a public
issue.

## What is checked at runtime

Every run, before searching:

- scalar 1 maps to the Ed25519 base point;
- RFC 8032 test vector 1 reproduces the published public key;
- the incremental chain and batch inversion are compared against full
  double-and-add scalar multiplication over 768 consecutive keys.

All three are fatal on failure. Every candidate is additionally re-derived from its
final scalar by full scalar multiplication and cross-checked against the incremental
chain, and the host re-derives the address from the public key independently before
writing. `verify.py` re-checks written keys in pure Python with no shared code.

## Known limitations

- **Not constant-time.** Scalar multiplication branches on secret bits. Acceptable
  for local vanity generation; do not reuse this code for Ed25519 signing.
- Discarded keys live briefly in GPU local memory, which this program does not wipe.
- Keys are only as good as `getrandom(2)` on the host.

## History

Before commit history began, this program seeded all key material from
`time(NULL)`. Two runs started in the same second produced identical keys, and
anyone knowing an address and roughly when it was generated could re-derive the
secret key with a feasible search. **Any address generated by such a build should
not be used as a service identity.** Current builds draw a fresh 32-byte root from
`getrandom(2)` for every kernel launch.
